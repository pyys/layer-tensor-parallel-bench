# layer-tensor-parallel-bench

### llama.cpp 레이어 분산 vs 텐서 병렬 실측 — GPU와 인터커넥트를 바꿔가며. 시작점은 PCIe Gen1 x4 (약 1 GB/s)

**공식 문서에 없는 숫자를, 하나의 동결된 방법으로.**

llama.cpp 에는 공식 [multi-GPU 안내서](https://github.com/ggml-org/llama.cpp/blob/master/docs/multi-gpu.md)
가 있고, 각 분할 방식이 무엇을 위한 것인지 서술한다. 그런데 **벤치마크 수치가
하나도 없다.** 이 저장소가 그 숫자를 채운다. 시작점은 극단적인 조건이다 —
**채굴용 GPU 4장, PCIe Gen1 x4, NVLink 없음.**

통념에 따르면 이는 극히 느린 인터커넥트에 해당하므로 텐서 병렬이 아닌 **레이어
병렬이 권장**되고, **MTP 를 켜면 더 높은 생성 속도**를 얻을 수 있다. 작성자도 그
통념대로 **레이어 병렬 + MTP 켬** 으로 운용하고 있었다. 실험 결과 그 조합은
**12개 조건 중 가장 낮은 생성 속도**를 내는 설정이었다.

측정 대상은 실제 대화에서 일어나는 일이다. 수만 토큰짜리 콜드 프리필 한 번,
그 뒤 프롬프트 캐시가 적중하는 웜 턴 여러 번. **분할 방식의 우열이 이 둘에서
뒤집히므로**, 한쪽만 재는 합성 벤치는 틀린 답을 준다.

## ⚠️ 재기 전에: NCCL 부터 설치할 것

`GGML_CUDA_NCCL` 은 **기본값이 ON** 이다. 그런데 **NCCL 은 CUDA 에 포함돼 배포되지
않는다.** 직접 설치해야 한다. 공식 안내서도 그렇게 적고 있다. 안 적혀 있는 것은
그 대가가 얼마인지, 그리고 **내장 폴백이 GPU 2장 전용**이라는 사실이다.

```
W NCCL not compiled in; falling back to internal AllReduce.
W internal AllReduce init failed (n_devices != 2?); falling back to meta-backend butterfly
```

cmake 는 경고만 낸다(`Could NOT find NCCL`). 서버도 경고만 낸다. **전부 그대로
돌아간다 — 3분의 1 속도로.**

| 4장, Qwen3.6-27B Q6_K | NCCL 없음 | NCCL |
|---|---|---|
| tensor pp512 | 61.15 | **190.48** (+211%) |
| tensor tg128 | 13.19 | **18.39** (+39%) |
| layer (대조) | 변화 없음 | 변화 없음 |

폴백 상태에서 재면 *"텐서 병렬은 프리필을 팔아 디코드를 산다"* 는 결론이 나온다.
그건 측정 오류다. **이 저장소의 첫 측정이 정확히 그 함정에 빠져 결론을 한 번
뒤집어야 했다.**

## 발견

*(아직 플랫폼 하나뿐이다. 플랫폼이 늘 때마다 일반화 가능 여부를 다시 확인한다.
근거는 [docs/p104-100-x4.ko.md](docs/p104-100-x4.ko.md))*

### 1. "배치 1은 대역폭 바운드라 검증이 공짜" — 모든 카드에서 그렇지는 않다

투기적 디코딩의 표준 설명은 이렇다. **배치 1에서 GPU 는 메모리 대역폭 바운드라
대부분 놀고 있으므로, 드래프트 토큰 몇 개를 검증하는 비용이 거의 0이다.**
이 전제가 투기적 디코딩을 성립시킨다.

**이 하드웨어에서는 배치 1에서도 그 전제가 깨진다.** 배치 4 검증이 단일 토큰의
**2.25~2.42배**가 든다. 카드가 배치 1에서 이미 연산 바운드이기 때문이다.

| | layer 4장 | tensor 4장 |
|---|---|---|
| 배치 약 4의 비용 배수 | 2.25 | 2.42 |
| 스텝당 산출 토큰 | 1.89 | 1.99 |
| **손익분기 수락률** | **42.3%** | **47.8%** |
| 실측 수락률 | 29.9% | 33.1% |
| 실측 손실 | **−16.3%** | **−17.2%** |

비용 모델이 예측한 손실과 실측이 **0.9%p 안에서 일치**한다.

문헌의 경험칙인 "수락률 50% 아래면 손해"는 보통 **배치 크기의 문제**로 서술된다.
여기서는 **카드의 문제**다. 레짐을 정하는 것은 동시 시퀀스 수가 아니라
**연산 대 대역폭 비율**이다.

**방법은 재사용 가능하다.** `스텝 수 = n_predict − 수락 수` 로 어느 llama.cpp
실행에서든 비용 배수를 바로 뽑을 수 있다. METHOD 5절 참조.

대조로, 같은 llama.cpp MTP 기능의 공개 측정치는 이렇다.

| 출처 | 하드웨어 | 수락률 | 속도 |
|---|---|---|---|
| [PR #22673](https://github.com/ggml-org/llama.cpp/pull/22673) | — | — | 약 **2배** (1.2~2배 분포) |
| [RTX PRO 6000](https://jarvislabs.ai/blog/qwen36-mtp-llamacpp-rtxpro6000) | RTX PRO 6000 | — | **1.73배** |
| [sudoingX/qwen38-mtp](https://github.com/sudoingX/qwen38-mtp) | 소비자 GPU | 0.797 / 0.732 | **2.07 / 2.33배** |
| **본 측정** | **P104-100 ×4** | **0.299 / 0.331** | **0.84 / 0.83배** |

**같은 기능이 한쪽에서는 속도를 두 배로 만들고 다른 쪽에서는 손해다.** 그리고
그 대조는 논리를 되돌려 읽게 한다 — 수락률 75%에 2배가 나온다는 것은 **그 카드들
에서 배치 1 검증이 거의 공짜**, 곧 **대역폭 바운드**라는 뜻이다.

⚠️ 위 수치들은 본 저장소의 방법론으로 측정한 것이 아니며 모델·양자화·설정이
제각각이다. 엄밀한 대조군이 아니라 참고용이다.

### 2. 레이어 분산은 디코드 이득이 0이다 — 정량화

공식 안내서는 레이어 분산이 "느린 인터커넥트에 관대"하고 텐서 모드가 "토큰 생성
우선"이라고 적는다. 그 차이의 크기는 이렇다.

| GPU 수 | 2 | 3 | 4 |
|---|---|---|---|
| tg (t/s) | 8.08 | 7.97 | 7.82 |

편차 3%, 그나마 **카드가 많을수록 조금 느리다.** 텔레메트리가 이유를 보여준다 —
한 장이 100%, 나머지는 0%, 순번대로 회전. 토큰 생성은 층을 순서대로 타므로
한 시점에 한 장만 계산한다.

→ **레이어 분산에서 추가 카드가 사는 것은 VRAM 과 긴 프리필뿐이다.**

### 3. 텐서 병렬 2장이 레이어 분산 4장을 이긴다

| 구성 | 웜 턴 |
|---|---|
| layer 4장 | 59.7초 |
| **tensor 2장** | **36.9초** |
| tensor 4장 | **28.1초** |

**카드 절반으로 1.6배 빠르다.** 세션 손익분기는 **1.2턴**(tensor 4장) /
**2.4턴**(tensor 2장) — 두세 번째 메시지부터 뒤집힌다.

메모리도 덜 쓴다. 실제 운용 설정(Q6_K, `-c 90000`) 기준:

| | 카드별 (MiB) | 편차 | 최소 여유 |
|---|---|---|---|
| 레이어 분할, 손으로 튜닝한 `-ts` | 7565 / 7253 / 7583 / 7699 | 446 | **410** |
| **텐서 병렬** | **6823 × 4** | **0** | **1,286** |

**2.8GB 덜 쓰면서 첫 로드에 균등하다.** 위 레이어 분할 값은 **여섯 번 재기동해서**
찾았고, 그 직전 시도는 아예 로드에 실패했다. 한 번 찾으면 그대로 쓰므로 일상적
부담은 아니지만, **초기 구축과 업그레이드 시점의 비용**이다 — 모델을 바꾸거나
카드를 추가할 때마다 반복된다.

같은 운용 설정으로 비공개 픽스처에서 전체 비교를 다시 돌린 결과:
**웜 턴 58.4초 → 30.4초(1.92배), 생성 8.22 → 16.24 t/s.** 손익분기는 0.23턴으로
첫 웜 턴부터 B 가 이긴다. 상세는
[보고서 2-6절](docs/p104-100-x4.ko.md#2-6-운용-설정에서의-재확인-q6_k--c-90000).

### 4. 콜드와 웜에서 우열이 뒤집힌다

| | 콜드 23k 토큰 | 웜 약 700 토큰 |
|---|---|---|
| layer 4장 | **327.3 t/s** | 85.3 t/s |
| tensor 4장 | 171.4 t/s | **128.8 t/s** |

긴 프리필은 레이어가 1.9배, 짧은 프리필은 텐서가 1.5배 빠르다. 같은 하드웨어에서
`llama-bench` 의 `pp512` 는 **정반대 순위**를 준다. 마이크로배치가 한둘뿐이라
레이어 파이프라인을 채우지 못하기 때문이다.

**합성 프리필 벤치로 분할 방식을 고르면 안 된다.**

그리고 프롬프트 캐시가 적중하면 **웜 턴의 86%가 디코드**다. 사용자 체감을 정하는
것은 콜드가 아니라 웜이다.

### 5. 텐서 병렬 스케일링 효율은 2장에서 이미 꺾인다

| N | 1장 대비 | 효율 |
|---|---|---|
| 2 | 1.62배 | **81%** |
| 3 | 1.77배 | **59%** |
| 4 | 2.29배 | **57%** |

카드를 늘리는 전략은 4장 근처가 한계다. 3장이 특히 나쁜 것은 NCCL 알고리즘이
2의 거듭제곱에서 유리하기 때문으로 보이나 **미검증**이다.

⚠️ 여기서 1장 기준선은 실측이 아니라 환산값이다 — 한계 절 참조.

### 6. 연산 바운드 카드에서 양자화는 속도 수단이 아니다

| | 모델 크기 | tensor 4장 tg |
|---|---|---|
| Q6_K | 20.88 GiB | 18.39 |
| Q3_K_M | 12.81 GiB | **17.89** |

바이트를 39% 덜 읽는데 속도가 같고, 루프라인으로도 사양 대역폭의 19~34%만 쓴다.
**여기서 양자화는 적재(capacity) 수단이지 속도 수단이 아니다.** 발견 1과
독립적인 경로로 같은 결론에 도달한다.

## 방법

크면 N=2 셀이 끊겨 스케일링 곡선에 구멍이 난다.

## 재현

```bash
# 0) NCCL 부터 설치한다. CUDA 에 포함돼 있지 않다.
#    CUDA 버전을 맞출 것 — 기본 후보가 더 최신 CUDA 를 겨냥할 수 있다.
apt-get install -y libnccl2=<버전>+cuda<사용중인CUDA> libnccl-dev=<버전>+cuda<사용중인CUDA>

# 1) 빌드. cmake 가 "Found NCCL" 을 찍는지 확인할 것 ("Could NOT find NCCL" 이면 실패)
cmake -S llama.cpp -B llama.cpp/build -DGGML_CUDA=ON \
  -DCMAKE_CUDA_ARCHITECTURES=<아키텍처> -DCMAKE_BUILD_TYPE=Release -DGGML_CUDA_NCCL=ON
cmake --build llama.cpp/build --config Release -j 8

# 2) 모델 양자화 (원본은 HuggingFace, METHOD 1-1 참조)
llama-quantize --tensor-type blk.64=q8_0 RVN-BF16-mtp.gguf qwen38-heretic-Q3KM-mtp.gguf Q3_K_M

# 3) 픽스처 생성 — 위키문헌에서 고정 리비전을 받아 조립
python3 harness/make_fixture.py --pin          # 최초 1회
python3 harness/make_fixture.py --port 8099 --out fixtures/mujeong.json

# 4) 토큰 수 확인 (건너뛰지 말 것 — 초과하면 조용히 잘린다)
python3 harness/server_bench.py --check

# 5) 측정
python3 harness/server_bench.py
```

중단 후 재실행하면 완료된 셀은 건너뛴다.

## 픽스처

이광수 「무정」(1917, **퍼블릭 도메인**)을 한국어 위키문헌에서 받아 짧은 `user`
턴과 긴 `assistant` 턴이 번갈아 나오는 대화로 재구성한다.

텍스트는 저장소에 넣지 않는다. `harness/fixture.lock.json` 에 **리비전 ID 가
고정**돼 있어 누가 언제 돌려도 바이트 단위로 같은 픽스처가 나온다.

⚠️ **픽스처는 한국어이고 1917년 표기법이다.** 자당 토큰 수와 예측 가능성이
언어·시대에 따라 다르므로 **영어 벤치마크와 직접 비교하면 안 된다.** 특히 MTP
수락률이 픽스처에 민감하다 — P104 보고서 부록 A 에 같은 셀을 다른 픽스처로 돌린
결과가 있다.

## 한계

1. **1장 기준선이 모든 플랫폼에서 실측되지는 않는다.** 모델(13,115 MiB)이 한 장에
   안 들어가면 레이어 분산의 `tg` 로 대용한다. **발견 5가 이 환산에 의존한다.**
   해당하는 보고서에는 명시한다
2. **셀당 1회 실행.** 웜 4턴이 셀 내 변동을 보여주지만 실행 간 재현성은 측정하지
   않았다
3. **모델 1종·양자화 1종.** 아키텍처가 다르면(특히 full attention 비율이 다르면)
   결과가 달라질 수 있다
4. **`ignore_eos` 가 MTP 수락률을 낮춘다.** 모델이 끝내려는 지점을 넘겨 생성하므로
   실사용보다 낮게 나온다. **발견 1의 판정은 손익분기 역산에 의존**하며 직접
   측정이 아니다
5. 플랫폼별 한계는 각 보고서 7절에 있다
