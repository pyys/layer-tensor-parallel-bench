# NVIDIA P104-100 8GB ×4 — 레이어 병렬 vs 텐서 병렬

측정일 2026-09-10. 방법론 **METHOD v1.1** ([`../METHOD.ko.md`](../METHOD.ko.md)).
원시 데이터 [`../results/p104-100-x4.jsonl`](../results/p104-100-x4.jsonl).
파생 지표는 별도 문서 [`p104-100-x4-metrics.ko.md`](p104-100-x4-metrics.ko.md).

> 측정 조건은 METHOD 에 있다. 여기에는 이 플랫폼의 환경·결과·해석만 적는다.
>
> ⚠️ **영문 [`p104-100-x4.md`](p104-100-x4.md) 이 정본이다.**

**P104-100 은 채굴 전용으로 팔린 GP104 파생 카드다.** 디스플레이 출력이 없고
PCIe 레인이 Gen1 x4 로 제한돼 있다. 다중 GPU LLM 추론에서 이 카드가 어떻게
동작하는지에 대한 공개 자료가 없어서 이 측정을 시작했다.

---

## 1. 환경

### 하드웨어

| 항목 | 값 |
|---|---|
| GPU | NVIDIA P104-100 8GB ×4 (GP104, sm_61, Pascal) |
| VRAM | 8,109 MiB / 장, 32,437 MiB 합계 (가용 8,023 MiB / 장) |
| 사양 메모리 대역폭 | 약 320 GB/s (GDDR5X 256-bit) |
| CPU / RAM | AMD EPYC 7232 8코어 / 32GB |

**PCIe 링크** — `Gen1 x4 가 최대치`다. 유휴 다운시프트가 아니라 하드웨어 천장이며,
부하 중에도 동일하다.

```
index, pcie.link.gen.current, pcie.link.gen.max, pcie.link.width.current, pcie.link.width.max
0, 1, 1, 4, 4
1, 1, 1, 4, 4
2, 1, 1, 4, 4
3, 1, 1, 4, 4
```

**토폴로지** — `nvidia-smi topo -m` 출력 그대로.

```
        GPU0    GPU1    GPU2    GPU3    CPU Affinity    NUMA Affinity   GPU NUMA ID
GPU0     X      NODE    NODE    NODE    0-15            0               N/A
GPU1    NODE     X      NODE    NODE    0-15            0               N/A
GPU2    NODE    NODE     X      PHB     0-15            0               N/A
GPU3    NODE    NODE    PHB      X      0-15            0               N/A

  NODE = Connection traversing PCIe as well as the interconnect between
         PCIe Host Bridges within a NUMA node
  PHB  = Connection traversing PCIe as well as a PCIe Host Bridge (typically the CPU)
```

NVLink 도 PCIe 스위치도 없다. GPU2–GPU3 만 호스트 브리지 하나(PHB)를 거치고
나머지 전 쌍은 브리지를 여럿 거친다(NODE).

**P2P** — `nvidia-smi topo -p2p r` 기준 전 쌍 `OK`.

### 모델

원본은 HuggingFace 저장소
`0bserverx/Qwen3.8-27B-Heretic-Abliterated-Uncensored-GGUF` 의
**`RVN-BF16-mtp.gguf`** (54.3 GB, BF16, MTP 헤드 포함). 이 파일을 받아 직접
양자화했다.

```
llama-quantize --tensor-type blk.64=q8_0 RVN-BF16-mtp.gguf qwen38-heretic-Q3KM-mtp.gguf Q3_K_M
```

`--tensor-type blk.64=q8_0` 은 필수다. 원본의 MTP 헤드(`blk.64`)가 이미 q8_0 이라
그냥 돌리면 `requantizing from type q8_0 is disabled` 로 실패한다. 이 지정으로
해당 블록은 재양자화 없이 복사된다.

| 항목 | 값 |
|---|---|
| 크기 | **13,752,763,616 바이트 (13,115 MiB)** |
| sha256 | `727e7d8b3ab3af1a6eeb166f3d7aac93d51ac0cdc06200e8f1cbac9074591ca4` |

Q3_K_M 을 고른 것은 품질 때문이 아니라 **8GB 카드 2장에 들어가는 최대 크기**이기
때문이다. 이보다 크면 N=2 셀을 잴 수 없어 스케일링 곡선이 끊긴다.

---

> ## ⚠️ NCCL 라이브러리가 없으면 이 측정은 무효다
>
> `GGML_CUDA_NCCL` 은 **기본값이 ON** 이지만
> [NCCL 은 CUDA 에 포함돼 배포되지 않는다](https://github.com/ggml-org/llama.cpp/blob/master/docs/multi-gpu.md).
> 직접 설치해야 하고, **플래그를 줬다는 사실만으로는 아무것도 보증되지 않는다.**
> cmake 는 `Could NOT find NCCL` 경고만 내고 그대로 빌드한다.
>
> 라이브러리 없이 4장 텐서 병렬을 띄우면:
>
> ```
> W NCCL not compiled in; falling back to internal AllReduce.
> W internal AllReduce init failed (n_devices != 2?); falling back to meta-backend butterfly
> ```
>
> **내장 AllReduce 는 GPU 2장 전용이다.** 3장 이상이면 초기화에 실패하고 폴백을
> 탄다. 공식 안내서에도 이 제약은 적혀 있지 않다. **전부 그대로 돌아간다** —
> 텐서 경로만 3배 느린 채로.
>
> | 4장, Qwen3.6-27B Q6_K | NCCL 없음 | NCCL |
> |---|---|---|
> | tensor **pp 512** | 61.15 | **190.48** (+211%) |
> | tensor **tg 128** | 13.19 | **18.39** (+39%) |
> | layer (대조) | 변화 없음 | 변화 없음 |
>
> 폴백 상태에서 재면 *"텐서 병렬은 프리필을 팔아 디코드를 산다"* 는 결론이 나온다.
> **그건 측정 오류다.** 이 저장소의 첫 측정 과정에서 이 함정이 발견되어
> **실험을 중단하고 처음부터 다시 측정했다.**
>
> *(위 llama-bench 수치는 동결 방법론 밖의 보조 측정이다. `pp 512` 는 512토큰
> 프롬프트 처리, `tg 128` 은 128토큰 생성을 뜻한다.)*

### 2-6. 운용 설정에서의 재확인 (Q6_K, `-c 90000`)

> ⚠️ 이 절은 **동결 방법론 밖의 보조 측정**이다. 매트릭스는 Q3_K_M / `-c 27000` /
> `-ts` 미지정으로 돌았지만, 여기서는 실제 운용 설정인 **Q6_K / `-c 90000`** 과
> 손으로 튜닝한 `-ts` 를 쓴다. **매트릭스 결론이 운용 조건으로 옮겨가는지**를
> 확인하는 것이 목적이다. 프롬프트는 부록 A 의 비공개 픽스처.

비교 대상은 **작성자가 실제로 쓰던 설정**(레이어 분할 + MTP)과 매트릭스가 지목한
최적 설정(텐서 병렬 + MTP 끔)이다.

| | A: 기존 운용 | B: 텐서·MTP 끔 | 배수 |
|---|---|---|---|
| 콜드 프리필 | **222.9 t/s** | 170.8 t/s | A 1.31배 |
| 콜드 총 소요 | **152.4초** | 158.9초 | A 1.04배 |
| 웜 프리필 | 75.9 t/s | **127.3 t/s** | **B 1.68배** |
| **생성** | 8.22 t/s | **16.24 t/s** | **B 1.98배** |
| **웜 턴** | 58.4초 | **30.4초** | **B 1.92배** |
| MTP 수락률 | 37.0% | — | |

```
A = 152.4 + 58.4N        B = 158.9 + 30.4N
손익분기 = 6.5 / 28.0 = 0.23턴
```

**첫 웜 턴부터 B 가 이긴다.** 10턴 대화로 환산하면 736초 → 463초, **37% 단축**이다.

A 는 유리한 조건을 모두 갖고 붙었다 — 여섯 번 튜닝한 `-ts`, 통념대로 켠 MTP,
그리고 무정 픽스처(29.9%)보다 수락률이 높은 픽스처(37.0%). 그런데도 생성에서
절반이다.

매트릭스(Q3 / 27k)에서는 배수가 2.73배였는데 여기서는 1.98배다. 양쪽 다 이유가 있다 —
**A 가 빨라진 것**은 이 픽스처의 MTP 수락률이 더 높아서고(그래도 손익분기 42.3%
에는 못 미친다), **B 가 느려진 것**은 컨텍스트가 27k → 90k 로 늘어 KV 가 커졌기
때문이다. 두 픽스처·두 양자화·두 컨텍스트에서 **방향과 크기가 일관된다.**

### VRAM 배분

같은 모델, 같은 컨텍스트에서 로드 직후 VRAM:

| | 카드별 (MiB) | 편차 | 최소 여유 | 합계 |
|---|---|---|---|---|
| 레이어 분할 (`-ts 18,17,17,14`) + MTP | 7565 / 7253 / 7583 / 7699 | 446 | **410** | 30,100 |
| **텐서 병렬 4장, MTP 없음** | **6823 / 6823 / 6823 / 6823** | **0** | **1,286** | **27,292** |

**텐서 병렬이 2.8GB 를 덜 쓰고, 편차가 0이다.** 이유는 둘이다 — MTP 드래프트
컨텍스트(약 0.5GB)가 없고, 텐서 병렬은 출력 텐서와 KV 를 카드별로 쪼개므로
레이어 분할처럼 마지막 카드에 몰리지 않는다.

### 그 `-ts` 값을 찾는 데 여섯 번의 재기동이 들었다

레이어 분할에서 위 배분에 도달하기까지의 과정이다.

| 시도 | 조건 | 카드별 VRAM | 편차 |
|---|---|---|---|
| 1 | `-c 512` 균등, MTP 끔 | 5501 / 5187 / 5501 / 5557 | 370 |
| 2 | `-c 512` `-ts 16,18,16,16` | 5187 / 5813 / 5187 / 6203 | 1016 |
| 3 | `-c 32000` 균등, MTP 켬 | 6621 / 6271 / 6621 / 7457 | 1186 |
| 4 | `-c 80000` `-ts 17,17,17,15` | 7055 / 7055 / 7055 / 8064 | 1009 |
| 5 | `-c 90000` `-ts 17,17,17,15` | **로드 실패** | — |
| 6 | `-c 90000` `-ts 18,17,17,14` | 7563 / 7251 / 7581 / 7697 | **446** |

5번의 실패 로그:

```
ggml_backend_cuda_buffer_type_alloc_buffer: allocating 554.06 MiB on device 3: cudaMalloc failed: out of memory
```

**레이어 하나를 잘못 배분하면 목표 컨텍스트가 아예 안 뜬다.** 그리고 배분은
모델·컨텍스트·MTP 유무가 바뀔 때마다 다시 잡아야 한다 — 카드별 고정비가 다르기
때문이다(마지막 카드가 출력 텐서를, 첫 카드가 컨텍스트 비례 연산 버퍼를 진다).

한 번 찾으면 그대로 쓰므로 일상적인 운용 부담은 아니다. **초기 구축과 업그레이드
시점의 비용**이다 — 모델을 바꾸거나 카드를 추가할 때마다 이 과정을 반복해야 한다.
텐서 병렬은 첫 로드에 균등하게 잡히므로 그 비용이 없다.

## 3. 해석

> ⚠️ **이 절과 4절은 V100 16GB PCIe ×4 측정 결과가 나오면 수정될 수 있다.**
> 특히 스케일링 효율과 MTP 관련 해석은 단일 플랫폼에서 나온 것이라, 다른 카드에서
> 같은 패턴이 나오는지 확인되기 전까지는 **이 하드웨어에 한정된 관찰**로 읽어야 한다.

파생 지표(세션 손익분기, 스케일링 효율, MTP 배치 경제학, 루프라인)의 수치와
계산 과정은 [`p104-100-x4-metrics.ko.md`](p104-100-x4-metrics.ko.md) 에 있다.

### 3-1. 레이어 분산은 디코드에서 카드를 쓰지 않는다

| N | tg |
|---|---|
| 2 | 8.08 |
| 3 | 7.97 |
| 4 | 7.82 |

편차 3%, 그나마 **카드가 많을수록 조금 느리다**(파이프라인 오버헤드).

텔레메트리가 이유를 보여준다 — **한 장이 100%, 나머지는 0%, 순번대로 회전**한다.
토큰 생성은 층을 순서대로 타므로 한 시점에 한 장만 계산한다.

프리필은 다르다. 마이크로배치를 카드 간에 겹칠 수 있어 콜드 pp 가
212.7 → 259.3 → 327.3 으로 카드 수에 따라 늘어난다.

→ **레이어 분산에서 추가 카드가 사는 것은 (a) VRAM 과 (b) 긴 프리필뿐이다.**

### 3-2. 콜드와 웜에서 우열이 뒤집힌다

| | 콜드 (23,037tok) | 웜 (637~790tok) |
|---|---|---|
| layer 4장 | **327.3** | 85.3 |
| tensor 4장 | 171.4 | **128.8** |

**긴 프리필은 레이어가 1.9배 빠르고, 짧은 프리필은 텐서가 1.5배 빠르다.**

23k 는 마이크로배치가 수십 개라 레이어 파이프라인이 꽉 차지만, 텐서는 배치마다
all-reduce 를 낸다. 반대로 700토큰은 배치가 한둘이라 레이어가 파이프라인을 못
채운다 — 그래서 **웜 pp 가 N 과 무관하게 85 t/s 로 고정**된다.

→ **합성 벤치를 실사용 프리필의 대표값으로 쓰면 안 된다.** 같은 하드웨어에서
`llama-bench` 의 `pp 512` 는 텐서 우세(190 vs 152), 실측 23k 콜드는 레이어
우세(171 vs 327)다. **정반대 결론이 나온다.**

### 3-3. 디코드가 실사용을 지배한다

웜 턴의 시간 배분 (layer 4장):

| | 시간 | 비중 |
|---|---|---|
| 프리필 (729tok @ 85.3) | 8.5초 | 14% |
| **생성 (400tok @ 7.82)** | **51.2초** | **86%** |

프롬프트 캐시가 적중하면 프리필이 23,037 → 약 700토큰으로 줄어들기 때문이다
(`cache_n` 22,521 → 24,646). **콜드에서 91% 였던 프리필 비중이 웜에서 14% 로
떨어지고, 워크로드가 생성 지배로 바뀐다.**

레이어 분산은 바로 그 생성 단계에서 카드를 못 쓴다.

### 3-4. 플랫폼에 따라 추론에서도 대역폭 바운드가 아닐 수 있다

| | 모델 크기 | tensor 4장 tg |
|---|---|---|
| Q6_K | 20.88 GiB | 18.39 *(llama-bench, 저컨텍스트)* |
| Q3_K_M | 12.81 GiB | **17.89** *(본 측정, 23k 컨텍스트)* |

바이트를 **39% 덜 읽는데 속도가 같다.** Q3 쪽이 컨텍스트가 훨씬 길어 불리한
조건인데도 그렇다. 루프라인으로도 사양 대역폭의 19~34%만 쓴다.

일반적으로 디코드는 메모리 대역폭 바운드이고, 그래서 **양자화를 낮추면 빨라진다**
— 읽을 바이트가 줄기 때문이다. **이 카드에서는 그 전제가 성립하지 않는다.**
양자화는 여기서 적재(capacity) 수단일 뿐이다.

이것은 이 플랫폼에 대한 관찰이지 일반 명제가 아니다. 대역폭 바운드인 카드에서는
양자화가 여전히 속도 수단이다.

⚠️ 두 값은 하네스가 다르다(llama-bench vs 서버). 이 비교 하나만으로는 약하지만,
3-5 가 **독립적인 경로로 같은 결론**에 도달한다.

### 3-5. 이 플랫폼에서 투기적 디코딩이 무의미한 이유는 "배치 4의 비용"이다

투기적 디코딩 문헌의 표준 전제는 **"배치 1은 대역폭 바운드라 검증이 거의 공짜"**
다. 이 하드웨어에서는 배치 1에서도 그 전제가 깨진다 — **배치 4 검증이 단일 토큰의
2.25~2.42배**가 든다.

메모리 대역폭 바운드 카드라면 가중치를 한 번만 읽으므로 배치 4가 거의 공짜여야
한다. **비용이 배치에 비례한다는 것은 연산 바운드라는 직접 증거**이며,
3-4 와 독립적으로 같은 결론에 도달한다.

그 결과 손익분기 수락률이 42~48% 로 높아진다. 실사용에서 관측한 수락률이
47.9% 이므로 **기껏해야 본전**이다. 계산 과정은
[파생 지표 문서](p104-100-x4-metrics.ko.md) 참조.

### 대조 — 다른 카드에서는 같은 기능이 두 배를 낸다

같은 llama.cpp MTP 기능의 공개 측정치다.

| 출처 | 하드웨어 | MTP 수락률 | 속도 |
|---|---|---|---|
| [PR #22673](https://github.com/ggml-org/llama.cpp/pull/22673) (MTP 도입) | — | — | 유리한 조건에서 약 **2배** (1.2~2배 분포) |
| [RTX PRO 6000 측정](https://jarvislabs.ai/blog/qwen36-mtp-llamacpp-rtxpro6000) | RTX PRO 6000 | — | **1.73배** (Qwen3.6 27B Dense) |
| [sudoingX/qwen38-mtp](https://github.com/sudoingX/qwen38-mtp) | 소비자 GPU | 0.797 / 0.732 | **2.07배 / 2.33배** |
| **본 측정** | **P104-100 ×4** | **0.299 / 0.331** | **0.84배 / 0.83배** |

마지막 행이 **우리 카드**다. 같은 기능이 한쪽에서는 속도를 두 배로 만들고 다른
쪽에서는 손해다.

그리고 이 대조는 3-5 의 논리를 되돌려 읽을 수 있게 한다 — **수락률 75%에 2배가
나온다는 것은 그 카드들에서 배치 1 검증이 거의 공짜라는 뜻**이고, 곧 그 카드들이
**대역폭 바운드**라는 뜻이다. 레짐을 정하는 것은 기능이 아니라 카드다.

⚠️ 위 수치들은 본 저장소의 방법론으로 측정한 것이 아니며 모델·양자화·설정이
제각각이다. **엄밀한 대조군이 아니라 참고용**이다.

반대 방향의 공개 사례도 있다 —
[RTX 3090 + Qwen3.6-35B-A3B 에서 모든 투기 모드가 baseline 보다 느렸다](https://hackmd.io/ODXuOQNzSiyUITz7g9mtBw)는
보고다. 다만 그쪽은 MoE 모델이라 원인이 다를 수 있고, 배치 비용 분해는 하지 않았다.

## 4. MTP 는 평균보다 분산이 문제다

> ⚠️ 3절과 마찬가지로 V100 측정 후 수정될 수 있다.

웜 4턴의 `tg` 편차:

| 셀 | 웜 4턴 tg | 편차 |
|---|---|---|
| tensor / MTP off / 4장 | 17.94 / 17.91 / 17.86 / 17.84 | **0.6%** |
| layer / MTP off / 2장 | 8.12 / 8.09 / 8.06 / 8.06 | 0.8% |
| layer / MTP on / 4장 | 6.51 / 6.19 / 6.63 / 6.86 | 10.1% |
| tensor / MTP on / 4장 | 13.17 / 13.92 / **17.90** / 14.28 | **31.9%** |
| tensor / MTP on / 3장 | 11.34 / **19.60** / 10.65 / 11.81 | **67.0%** |

`tensor / MTP on / 3장` 의 2턴째는 수락률 **75%**(368개 중 276개)를 찍어
19.60 t/s 가 나왔다. 예측하기 쉬운 대목을 만나면 MTP 가 빛나지만 **그런 구간이
언제 올지 모른다.**

평균이 손해인 데다 응답 시간까지 들쭉날쭉하므로, 체감 품질은 평균이 시사하는
것보다 나쁘다.

## 5. 부록 A — 비공개 픽스처 (재현 불가)

본 문서의 실험은 **비공개 픽스처를 대상으로 한 실험에서 출발했다**
(비공개 픽스처는 민감 데이터로 공개 불가).

다만 **본 문서의 공개된 실험 결과는 비공개 픽스처를 사용한 실험 결과 내용을 담고
있지 않으며**, 제시된 픽스처를 가지고 한 실험 데이터만을 포함하고 있다.

두 픽스처를 함께 기재하는 이유는 **MTP 를 끈 조건에서 1% 안에서 일치했기**
때문이다. 텍스트 성격이 크게 다른데도 같은 결과가 나왔다는 것은, 공개 결과가
텍스트에 좌우되지 않는다는 근거가 된다. 반면 **MTP 를 켠 조건에서는 차이가
났고, 그 대비 자체가 정보다.**

비공개 픽스처 관련으로는 **다음의 데이터만을 공개하니 이 데이터의 신뢰도는 직접
판단할 것.** 공개 픽스처와는 같은 하네스·같은 토큰 수·같은 셀 정의로 이루어졌다.

### MTP 없는 셀 — 1% 안에서 재현된다

| 셀 | 무정 | 비공개 | 차이 |
|---|---|---|---|
| layer / off / 4장 | 7.82 | 7.85 | −0.4% |
| layer / off / 3장 | 7.97 | 7.99 | −0.3% |
| layer / off / 2장 | 8.08 | 8.09 | −0.1% |
| tensor / off / 4장 | 17.89 | 17.91 | −0.1% |
| tensor / off / 3장 | 14.14 | 14.14 | 0.0% |
| tensor / off / 2장 | 13.06 | 12.96 | +0.8% |

**분할 방식과 GPU 수에 관한 결론은 텍스트 성격에 의존하지 않는다.**

### MTP 셀 — 픽스처에 민감하다

| 셀 | 무정 수락률 → tg | 비공개 수락률 → tg |
|---|---|---|
| layer / on / 4장 | 29.9% → 6.55 | **37.2% → 7.38** |
| tensor / on / 4장 | 33.1% → 14.82 | 34.9% → 15.29 |

자당 토큰 수는 실측으로 다르다 — **무정 1.843 자/토큰, 비공개 1.981 자/토큰.**

⚠️ **수락률 차이의 원인은 검증하지 못했다.** 두 픽스처는 시대(1917년 대 현대),
문체(소설 산문 대 대화체), 주제가 **동시에** 다르므로 어느 요인의 효과인지
분리할 수 없다. 텍스트의 예측 가능성 차이에서 기인한다고 **추정**할 뿐이다.

→ **MTP 관련 수치는 픽스처에 의존한다.** 절대값을 다른 환경에 옮기지 말 것.
반면 **"MTP 가 이 카드에서 손해"라는 방향은 두 픽스처에서 모두 성립**한다.

## 6. 이 플랫폼 고유의 한계

1. **GPU 1장 기준선이 환산값이다.** 모델(13,115 MiB)이 8GB 카드 한 장에 안 들어간다.
   [파생 지표 문서](p104-100-x4-metrics.ko.md)의 스케일링 효율이 이 환산에 의존한다.
   VRAM 이 더 큰 플랫폼에서 실측하면 타당성을 검증할 수 있다
2. **`layer / MTP on / 2장` 셀이 비어 있다.** 연산 버퍼 OOM
3. **텐서 병렬은 N 이 바뀌면 출력 자체가 달라진다.** `tensor / MTP on` 의 4·3·2장
   `draft_n` 이 전부 다르다(675/642/660 …). 연산 순서가 달라 생성 토큰이 달라지기
   때문이다. 반면 `layer / MTP on` 의 4장과 3장은 `draft_n`·`draft_n_accepted` 가
   턴마다 **완전히 동일**하다.
   → **텐서 병렬 셀 간 MTP 비교는 생성 내용이 통제되지 않는다**
