# NVIDIA P104-100 8GB ×4 — layer split vs tensor parallelism

Measured 2026-09-10. Methodology **METHOD v1.1** ([`../METHOD.md`](../METHOD.md)).
Raw data: [`../results/p104-100-x4.jsonl`](../results/p104-100-x4.jsonl).
Derived metrics live in [`p104-100-x4-metrics.md`](p104-100-x4-metrics.md).

> Measurement conditions live in METHOD. This document covers only this platform's
> environment, results and interpretation.
>
> *[한국어: `p104-100-x4.ko.md`](p104-100-x4.ko.md) — English is authoritative.*

**The P104-100 is a GP104 derivative sold for mining.** No display output, and the
PCIe link is capped at Gen1 x4. There is no published data on how it behaves for
multi-GPU LLM inference, which is why this measurement exists.

### Model

The source is **`RVN-BF16-mtp.gguf`** (54.3 GB, BF16, MTP head included) from the
HuggingFace repository
`0bserverx/Qwen3.8-27B-Heretic-Abliterated-Uncensored-GGUF`, quantized locally:

```
llama-quantize --tensor-type blk.64=q8_0 RVN-BF16-mtp.gguf qwen38-heretic-Q3KM-mtp.gguf Q3_K_M
```

`--tensor-type blk.64=q8_0` is required. The MTP head (`blk.64`) in the source is
already q8_0, so without it the run fails with
`requantizing from type q8_0 is disabled`. With it, that block is copied rather than
requantized.

> ## ⚠️ Without the NCCL library this measurement is void
>
> `GGML_CUDA_NCCL` **defaults to ON**, but
> [NCCL does not ship with CUDA](https://github.com/ggml-org/llama.cpp/blob/master/docs/multi-gpu.md).
> You have to install it, and **passing the flag proves nothing** — cmake prints
> `Could NOT find NCCL` and builds anyway.
>
> Bring up four-GPU tensor parallelism without the library:
>
> ```
> W NCCL not compiled in; falling back to internal AllReduce.
> W internal AllReduce init failed (n_devices != 2?); falling back to meta-backend butterfly
> ```
>
> **The built-in AllReduce is 2-GPU only.** With three or more it fails to initialize
> and takes a fallback path. The official guide does not mention this limit.
> **Everything keeps running** — roughly 3x slower on the tensor path.
>
> | 4 GPUs, Qwen3.6-27B Q6_K | No NCCL | NCCL |
> |---|---|---|
> | tensor **pp 512** | 61.15 | **190.48** (+211%) |
> | tensor **tg 128** | 13.19 | **18.39** (+39%) |
> | layer (control) | unchanged | unchanged |
>
> Measured in the fallback state, the conclusion comes out as *"tensor parallelism
> trades prefill for decode."* **That is a measurement error.** The trap surfaced
> during the first measurement run in this repository, which was **halted and redone
> from scratch.**
>
> *(Those llama-bench figures sit outside the frozen methodology. `pp 512` means a
> 512-token prompt processed; `tg 128` means 128 tokens generated.)*

### 2-6. Re-checked at production settings (Q6_K, `-c 90000`)

> ⚠️ This section is a **side measurement outside the frozen methodology**. The matrix
> ran Q3_K_M at `-c 27000` with no `-ts`; here the production settings are used —
> **Q6_K at `-c 90000`** with a hand-tuned `-ts`. The question is whether the matrix
> conclusion **carries over to production**. Prompts come from the private fixture in
> Appendix A.

The comparison is between **what the author was actually running** (layer split with
MTP) and the configuration the matrix identified as best (tensor parallelism, MTP off).

| | A: production | B: tensor, MTP off | Factor |
|---|---|---|---|
| Cold prefill | **222.9 t/s** | 170.8 t/s | A 1.31x |
| Cold total | **152.4 s** | 158.9 s | A 1.04x |
| Warm prefill | 75.9 t/s | **127.3 t/s** | **B 1.68x** |
| **Generation** | 8.22 t/s | **16.24 t/s** | **B 1.98x** |
| **Warm turn** | 58.4 s | **30.4 s** | **B 1.92x** |
| MTP acceptance | 37.0% | — | |

```
A = 152.4 + 58.4N        B = 158.9 + 30.4N
break-even = 6.5 / 28.0 = 0.23 turns
```

**B wins from the very first warm turn.** Over a ten-turn conversation that is
736 s → 463 s, a **37% reduction**.

A had every advantage — a `-ts` tuned over six reloads, MTP on as convention
recommends, and a fixture with higher acceptance (37.0%) than Mujeong's 29.9%. It
still generates at half the speed.

The matrix (Q3 at 27k) put the factor at 2.73x; here it is 1.98x. Both sides moved for
reasons that check out — **A got faster** because this fixture's MTP acceptance is
higher (still short of the 42.3% break-even), and **B got slower** because the context
grew from 27k to 90k, enlarging the KV cache. Across two fixtures, two quantizations
and two context sizes, **the direction and the magnitude stay consistent.**

### VRAM distribution

VRAM immediately after load, same model, same context:

| | Per card (MiB) | Spread | Min free | Total |
|---|---|---|---|---|
| Layer split (`-ts 18,17,17,14`) + MTP | 7565 / 7253 / 7583 / 7699 | 446 | **410** | 30,100 |
| **Tensor parallelism, 4 GPUs, MTP off** | **6823 / 6823 / 6823 / 6823** | **0** | **1,286** | **27,292** |

**Tensor parallelism uses 2.8 GB less and has zero spread.** Two reasons: there is no
MTP draft context (~0.5 GB), and tensor mode splits the output tensor and the KV cache
across cards instead of piling them onto the last one the way layer split does.

### Finding that `-ts` value took six reloads

The path to the layer-split distribution above:

| Attempt | Configuration | Per-card VRAM | Spread |
|---|---|---|---|
| 1 | `-c 512`, even, MTP off | 5501 / 5187 / 5501 / 5557 | 370 |
| 2 | `-c 512`, `-ts 16,18,16,16` | 5187 / 5813 / 5187 / 6203 | 1016 |
| 3 | `-c 32000`, even, MTP on | 6621 / 6271 / 6621 / 7457 | 1186 |
| 4 | `-c 80000`, `-ts 17,17,17,15` | 7055 / 7055 / 7055 / 8064 | 1009 |
| 5 | `-c 90000`, `-ts 17,17,17,15` | **failed to load** | — |
| 6 | `-c 90000`, `-ts 18,17,17,14` | 7563 / 7251 / 7581 / 7697 | **446** |

The failure at attempt 5:

```
ggml_backend_cuda_buffer_type_alloc_buffer: allocating 554.06 MiB on device 3: cudaMalloc failed: out of memory
```

**Misplace a single layer and the target context will not load at all.** And the
distribution has to be re-derived whenever the model, the context size or the MTP
setting changes, because the per-card fixed costs differ — the last card carries the
output tensor, the first carries a compute buffer that scales with context.

Once found, the value is simply reused, so this is not a day-to-day operational cost.
It is a **setup and upgrade cost** — the process repeats every time the model changes
or a card is added. Tensor parallelism balances itself on the first load and skips it
entirely.

## 3. Interpretation

> ⚠️ **This section and section 4 may be revised once the V100 16GB PCIe ×4
> measurement lands.** The scaling and MTP interpretations come from a single
> platform; until the same pattern is confirmed on another card, read them as
> **observations specific to this hardware**.

Numbers and derivations for session break-even, scaling efficiency, MTP batch
economics and the roofline are in
[`p104-100-x4-metrics.md`](p104-100-x4-metrics.md).

### 3-1. Layer split does not use your cards during decode

| N | tg |
|---|---|
| 2 | 8.08 |
| 3 | 7.97 |
| 4 | 7.82 |

Within 3%, and if anything **slower with more cards** (pipeline overhead).

Telemetry shows why — **one card at 100%, the others at 0%, rotating.** Token
generation walks the layers in order, so only one card computes at any instant.

Prefill is different. Micro-batches overlap across cards, so cold pp rises with card
count: 212.7 → 259.3 → 327.3.

→ **In layer split, additional cards buy (a) VRAM and (b) long prefill. Nothing else.**

### 3-2. Cold and warm prefill reverse the ranking

| | Cold (23,037 tok) | Warm (637–790 tok) |
|---|---|---|
| layer, 4 GPUs | **327.3** | 85.3 |
| tensor, 4 GPUs | 171.4 | **128.8** |

**Long prefill favours layer split by 1.9x; short prefill favours tensor by 1.5x.**

At 23k tokens there are dozens of micro-batches, so the layer pipeline stays full,
while tensor pays an all-reduce per batch. At 700 tokens there are only one or two
batches, so layer split cannot fill its pipeline — which is why **warm pp sits at
85 t/s regardless of N.**

→ **A synthetic benchmark must not stand in for real cold prefill.** On this same
hardware, `llama-bench`'s `pp 512` ranks tensor ahead (190 vs 152) while the measured
23k cold prefill ranks layer ahead (171 vs 327). **Opposite conclusions.**

### 3-3. Decode dominates real usage

Time breakdown of a warm turn (layer, 4 GPUs):

| | Time | Share |
|---|---|---|
| Prefill (729 tok @ 85.3) | 8.5 s | 14% |
| **Generation (400 tok @ 7.82)** | **51.2 s** | **86%** |

The prompt cache cuts prefill from 23,037 tokens to about 700 (`cache_n` 22,521 →
24,646). **Prefill goes from 91% of a cold turn to 14% of a warm one, and the
workload becomes generation-dominated.**

Generation is exactly where layer split cannot use the extra cards.

### 3-4. Inference is not always bandwidth-bound — it depends on the platform

| | Model size | tensor 4-GPU tg |
|---|---|---|
| Q6_K | 20.88 GiB | 18.39 *(llama-bench, short context)* |
| Q3_K_M | 12.81 GiB | **17.89** *(this measurement, 23k context)* |

Reading **39% fewer bytes gives the same speed**, and the Q3 figure is measured under
the harder condition of a far longer context. The roofline agrees — only 19–34% of
spec bandwidth is used.

Decode is normally memory-bandwidth-bound, which is why **dropping to a smaller
quantization normally makes it faster** — there are fewer bytes to read. **On this
card that premise does not hold.** Quantization here buys capacity, nothing more.

This is an observation about this platform, not a general claim. On a bandwidth-bound
card, quantization remains a speed lever.

⚠️ The two figures come from different harnesses (llama-bench vs the server). On its
own this comparison is weak — but 3-5 reaches the same conclusion **by an independent
route**.

### 3-5. On this platform, speculative decoding fails because a batch of 4 is not free

The standard account of speculative decoding assumes **batch 1 is memory-bound, so
verification is nearly free**. On this hardware that assumption breaks at batch 1 —
verifying a batch of 4 costs **2.25–2.42x** a single token.

On a bandwidth-bound card that batch would be nearly free, since the weights are read
once either way. **Cost scaling with batch size is direct evidence of a compute-bound
card**, and it is independent of the evidence in 3-4.

The consequence is a break-even acceptance rate of 42–48%. Acceptance measured in
real usage on this machine is 47.9%, so MTP is **at best break-even**. Derivation in
the [metrics document](p104-100-x4-metrics.md).

### Contrast — the same feature doubles speed on other cards

Published measurements of the same llama.cpp MTP feature:

| Source | Hardware | MTP acceptance | Speedup |
|---|---|---|---|
| [PR #22673](https://github.com/ggml-org/llama.cpp/pull/22673) (MTP support) | — | — | ~**2x** in favourable setups (spread 1.2–2x) |
| [RTX PRO 6000 measurement](https://jarvislabs.ai/blog/qwen36-mtp-llamacpp-rtxpro6000) | RTX PRO 6000 | — | **1.73x** (Qwen3.6 27B Dense) |
| [sudoingX/qwen38-mtp](https://github.com/sudoingX/qwen38-mtp) | consumer GPUs | 0.797 / 0.732 | **2.07x / 2.33x** |
| **This measurement** | **P104-100 ×4** | **0.299 / 0.331** | **0.84x / 0.83x** |

The last row is this card. **The same feature doubles speed on one and loses money on
another.**

The contrast also lets 3-5 be read backwards — **getting 2x at 75% acceptance means
verification at batch 1 really is nearly free on those cards**, which is to say they
are **bandwidth-bound**. The regime is set by the card, not by the feature.

⚠️ None of those figures were measured under this repository's methodology, and the
model, quantization and settings all differ. **They are a reference point, not a
control.**

A published result in the other direction also exists —
[every speculative mode tested on an RTX 3090 with Qwen3.6-35B-A3B came out slower
than baseline](https://hackmd.io/ODXuOQNzSiyUITz7g9mtBw). That is an MoE model, so the
cause may differ, and no batch-cost decomposition was done.

## 4. With MTP, the variance is worse than the average

> ⚠️ As with section 3, this may be revised after the V100 measurement.

Spread of `tg` across the four warm turns:

| Cell | Warm turns | Spread |
|---|---|---|
| tensor / MTP off / 4 | 17.94 / 17.91 / 17.86 / 17.84 | **0.6%** |
| layer / MTP off / 2 | 8.12 / 8.09 / 8.06 / 8.06 | 0.8% |
| layer / MTP on / 4 | 6.51 / 6.19 / 6.63 / 6.86 | 10.1% |
| tensor / MTP on / 4 | 13.17 / 13.92 / **17.90** / 14.28 | **31.9%** |
| tensor / MTP on / 3 | 11.34 / **19.60** / 10.65 / 11.81 | **67.0%** |

Turn 2 of `tensor / MTP on / 3` hit **75% acceptance** (276 of 368) and reached
19.60 t/s. When the model lands on a predictable passage, MTP shines — but **there is
no telling when that will happen.**

The average is already a loss; response times jumping around on top of that makes the
experience worse than the average suggests.

## 6. Limitations specific to this platform

1. **The single-GPU baseline is a substitution.** The model (13,115 MiB) does not fit
   on one 8GB card. The scaling efficiency in the
   [metrics document](p104-100-x4-metrics.md) depends on that substitution.
   Measuring it directly on a larger-VRAM platform would validate it
2. **`layer / MTP on / 2 GPUs` is missing** — compute-buffer OOM
3. **Tensor parallelism changes the output when N changes.** `draft_n` differs across
   the 4/3/2-GPU tensor MTP cells (675 / 642 / 660 ...) because the reduction order
   changes the generated tokens. By contrast the 4- and 3-GPU layer MTP cells have
   **identical** `draft_n` and `draft_n_accepted` on every turn.
   → **MTP acceptance is not controlled across tensor-parallel cells**
