# NVIDIA P104-100 8GB x4 — layer split vs tensor parallelism

Measured 2026-09-10. Methodology **METHOD v1.1** ([`../METHOD.md`](../METHOD.md)).
Raw data [`../results/p104-100-x4.jsonl`](../results/p104-100-x4.jsonl).
Derived metrics live in [`p104-100-x4-metrics.md`](p104-100-x4-metrics.md).

> Measurement conditions are in METHOD. This document holds only this platform's
> environment, results and interpretation.
> Conclusions that span platforms are in [`../FINDINGS.md`](../FINDINGS.md).

**The P104-100 is a GP104 derivative sold for mining.** It has no display output and
its PCIe lanes are capped at Gen1 x4. There was no public data on how this card
behaves in multi-GPU LLM inference, which is why this measurement exists.

> **This report was measured under v1.1.** It has none of the clock and throttle
> telemetry added in v1.2. The measurement conditions themselves are identical to
> v1.2, so the results still belong in the same table (METHOD section 8).

## 2. Results

- **Prefill (pp)** = how fast the prompt is read. `prompt_per_second`
- **Generation (tg)** = final output token rate. `predicted_per_second`
  (confirmed output, not drafts — `predicted_n = 400` on every turn)
- Cold is one run, warm is the mean of four turns
- **Percentages** are relative to **the slowest cell for that metric**, which is 100.
  The three baselines differ

| Metric | Baseline cell (100%) | Value |
|---|---|---|
| Cold pp | tensor / MTP on / 3 cards | 140.9 t/s |
| Warm pp | layer / MTP on / 4 cards | 77.1 t/s |
| tg | layer / MTP on / 4 cards | 6.55 t/s |

**Three things to read off this.**

1. **All six tensor-parallel cells beat all five layer-split cells.** The slowest
   tensor condition (2 cards, MTP on, 160%) is 30% faster than the fastest layer
   condition (2 cards, MTP off, 123%).
2. **The two `layer / MTP on` cells are last.** The configuration the author was
   running — "slow link, so layer plus MTP", exactly as the conventional advice says —
   turned out to be the slowest of the twelve. **On V100 this ranking inverts**
   (section 3-5).
3. **The cold pp ranking is an exact inversion of the tg ranking.** The cold leader
   (layer / MTP off / 4 cards, 232%) is ninth on generation (119%), and the generation
   leader (tensor / MTP off / 4 cards, 273%) manages only 122% cold. **Choose a
   configuration from one metric and you pay for it on the other.**

### 2-6. Re-check under production settings (Q6_K, `-c 90000`)

> ⚠️ This section is **a side measurement outside the frozen methodology**
> ([Notes and Caveats 3)](../FINDINGS.md#notes-and-caveats)). The matrix ran at
> Q3_K_M / `-c 27000` with no `-ts`; here the author's production settings of
> **Q6_K / `-c 90000`** and a hand-tuned `-ts` are used instead. The point is to see
> **whether the matrix conclusion carries over to production conditions.** The prompt
> is the private fixture from the appendix.

The comparison is between **what the author was actually running** (layer split plus
MTP) and what the matrix points to (tensor parallelism, MTP off).

| | A: previous production | B: tensor, MTP off | Ratio |
|---|---|---|---|
| Cold prefill | **222.9 t/s** | 170.8 t/s | A 1.31x |
| Cold total | **152.4s** | 158.9s | A 1.04x |
| Warm prefill | 75.9 t/s | **127.3 t/s** | **B 1.68x** |
| **Generation** | 8.22 t/s | **16.24 t/s** | **B 1.98x** |
| **Warm turn** | 58.4s | **30.4s** | **B 1.92x** |
| MTP acceptance | 37.0% | — | |

```
A = 152.4 + 58.4N        B = 158.9 + 30.4N
crossover = 6.5 / 28.0 = 0.23 turns
```

**B wins from the first warm turn.** Over a ten-turn conversation that is 736s down to
463s, **a 37% reduction.**

A entered the comparison with every advantage — a `-ts` tuned over six attempts, MTP
enabled as convention recommends, and a fixture with a higher acceptance rate than
Mujeong (37.0% against 29.9%). It still generates at half the speed.

The matrix (Q3 / 27k) gave a ratio of 2.73x where this gives 1.98x. Both moves have a
reason — **A got faster** because this fixture has a higher MTP acceptance rate (still
short of the 42.3% break-even), and **B got slower** because context grew from 27k to
90k and the KV cache with it. **Across two fixtures, two quantizations and two context
sizes, the direction and magnitude stay consistent.**

#### VRAM distribution

VRAM immediately after load, same model and same context:

| | Per card (MiB) | Spread | Smallest headroom | Total |
|---|---|---|---|---|
| Layer split (`-ts 18,17,17,14`) + MTP | 7565 / 7253 / 7583 / 7699 | 446 | **410** | 30,100 |
| **Tensor parallelism, 4 cards, MTP off** | **6823 / 6823 / 6823 / 6823** | **0** | **1,286** | **27,292** |

**Tensor parallelism uses 2.8GB less and is perfectly even.** Two reasons — there is
no MTP draft context (about 0.5GB), and tensor parallelism splits the output tensor
and the KV cache per card instead of piling them onto the last one.

#### Finding that `-ts` took six restarts

| Attempt | Condition | Per-card VRAM | Spread |
|---|---|---|---|
| 1 | `-c 512` even, MTP off | 5501 / 5187 / 5501 / 5557 | 370 |
| 2 | `-c 512` `-ts 16,18,16,16` | 5187 / 5813 / 5187 / 6203 | 1016 |
| 3 | `-c 32000` even, MTP on | 6621 / 6271 / 6621 / 7457 | 1186 |
| 4 | `-c 80000` `-ts 17,17,17,15` | 7055 / 7055 / 7055 / 8064 | 1009 |
| 5 | `-c 90000` `-ts 17,17,17,15` | **load failed** | — |
| 6 | `-c 90000` `-ts 18,17,17,14` | 7563 / 7251 / 7581 / 7697 | **446** |

The failure log from attempt 5:

```
ggml_backend_cuda_buffer_type_alloc_buffer: allocating 554.06 MiB on device 3: cudaMalloc failed: out of memory
```

**Misplace one layer and the target context will not come up at all.** And the
distribution has to be found again whenever the model, the context or the MTP setting
changes, because the fixed overhead differs per card (the last card carries the output
tensor, the first carries context-proportional compute buffers).

Once found it stays put, so this is not a daily operational burden. **It is the cost
of initial setup and of every upgrade.** Tensor parallelism loads evenly on the first
try and never pays it.

## 3. Interpretation

Figures and calculations for the derived metrics (session crossover, scaling
efficiency, MTP batch economics, roofline) are in
[`p104-100-x4-metrics.md`](p104-100-x4-metrics.md). Conclusions that span platforms are
in [`../FINDINGS.md`](../FINDINGS.md).

**Each section marks what the V100 measurement confirmed and what it overturned.**

### 3-1. Layer split does not use the cards during decode — same on V100

| N | tg |
|---|---|
| 2 | 8.08 |
| 3 | 7.97 |
| 4 | 7.82 |

A 3% spread, and if anything **more cards is slightly slower** (pipeline overhead).

The telemetry shows why — **one card at 100%, the rest at 0%, rotating in order.**
Token generation walks the layers in sequence, so only one card computes at a time.

Prefill is different. Micro-batches can overlap across cards, so cold pp rises with
card count: 212.7 → 259.3 → 327.3.

→ **What extra cards buy under layer split is (a) VRAM and (b) faster handling of long
prefills.**

**V100 confirmed this by measuring a single card** — 27.71 at one card against 27.29
at four, a 1.5% difference. That also validates the "layer tg = single-card speed"
derivation used here.

### 3-2. Cold and warm prefill rank the modes in opposite order — same on V100

| | Cold (23,037 tok) | Warm (637~790 tok) |
|---|---|---|
| layer 4 | **327.3** | 85.3 |
| tensor 4 | 171.4 | **128.8** |

**Long prefill favours layer by 1.9x; short prefill favours tensor by 1.5x.**

23k tokens is dozens of micro-batches, enough to fill the layer pipeline, while tensor
mode issues an all-reduce per batch. At 700 tokens there are one or two batches and
layer split cannot fill the pipeline — which is why **warm pp is pinned at 85 t/s
regardless of N.**

→ **Do not use a synthetic benchmark as a stand-in for real prefill.** On the same
hardware `llama-bench` `pp 512` favours tensor (190 against 152) while the measured
23k cold prefill favours layer (171 against 327). **The two disagree completely**
([Notes and Caveats 4)](../FINDINGS.md#notes-and-caveats)).

**The direction holds on V100 too** — layer ahead 1.75x cold, tensor ahead 1.22x warm.
Only the magnitude shrinks.

### 3-3. Decode dominates real use

Time split within a warm turn (layer, 4 cards):

| | Time | Share |
|---|---|---|
| Prefill (729 tok @ 85.3) | 8.5s | 14% |
| **Generation (400 tok @ 7.82)** | **51.2s** | **86%** |

When the prompt cache hits, prefill drops from 23,037 tokens to roughly 700
(`cache_n` 22,521 → 24,646). **Prefill goes from 91% of a cold turn to 14% of a warm
one, and the workload becomes generation dominated.**

Layer split is exactly the mode that cannot use extra cards during generation.

⚠️ This judgement assumes the author's usage pattern
([Notes and Caveats 9)](../FINDINGS.md#notes-and-caveats)).

### 3-4. On this platform decode is not bandwidth bound

| | Model size | tensor 4 tg |
|---|---|---|
| Q6_K | 20.88 GiB | 18.39 *(llama-bench, low context)* |
| Q3_K_M | 12.81 GiB | **17.89** *(this work, 23k context)* |

**39% fewer bytes read, same speed** — and the Q3 run is at a far longer context, which
should disadvantage it. The roofline puts utilization at 19~34% of spec.

Decode is normally memory bandwidth bound, which is why **dropping the quantization
usually makes it faster.** **On this card that premise does not hold.** Quantization
here is a capacity lever, nothing more.

⚠️ The two figures come from different harnesses
([Notes and Caveats 4)](../FINDINGS.md#notes-and-caveats)). The comparison is weak on
its own, but 3-5 reaches **the same conclusion by an independent route.**

> **No Q6 comparison was run on V100.** What V100 did add is a sweep that lowered only
> the core clock, measuring compute dependence directly —
> [FINDINGS 6](../FINDINGS.md). **The "compute bound" direction agrees across both
> platforms, but the conclusion in this section — that quantization is not a speed
> lever — is specific to P104.**

### 3-5. Speculative decoding is pointless here because a batch of four is expensive — and V100 flips it

The standard premise in the speculative decoding literature is that **batch 1 is
bandwidth bound, so verification is nearly free.** On this hardware the premise breaks
even at batch 1 — **verifying a batch of four costs 2.25~2.42x a single token.**

On a memory bandwidth bound card the weights are read once, so a batch of four should
be almost free. **Cost rising with batch size is direct evidence of a compute bound**,
reaching the same conclusion as 3-4 by an independent route.

The result is a break-even acceptance rate of 42~48%. The acceptance rate observed in
real use is 47.9%, so **at best it breaks even.** The calculation is in the
[derived metrics document](p104-100-x4-metrics.md).

> **The sign flips on V100.** Same methodology, same model, same binary — and
> **MTP gains 3.5% in layer mode.** Acceptance barely moves, 29.9% → 32.0%; what
> changes is **the cost multiple (2.25 → 1.89) and therefore the break-even line
> (42.3% → 29.9%).** Details in [FINDINGS 4](../FINDINGS.md).

#### Contrast — on other cards the same feature doubles throughput

Public measurements of the same llama.cpp MTP feature.

| Source | Hardware | MTP acceptance | Speed |
|---|---|---|---|
| PR #22673 [{ref 2.}](../FINDINGS.md#references) | — | — | about **2x** under favourable conditions |
| RTX PRO 6000 [{ref 3.}](../FINDINGS.md#references) | RTX PRO 6000 | — | **1.73x** |
| sudoingX/qwen38-mtp [{ref 4.}](../FINDINGS.md#references) | consumer GPUs | 0.797 / 0.732 | **2.07 / 2.33x** |
| **This work (P104)** | **P104-100 x4** | **0.299 / 0.331** | **0.84x / 0.83x** |
| This work (V100, layer) | V100 16GB x4 | 0.320 | **1.035x** |

**The same feature doubles throughput on one card and loses on another.** That
contrast also lets the logic in 3-5 be read backwards — **if 75% acceptance yields 2x,
then on those cards verifying at batch 1 really is nearly free**, which is to say they
are **bandwidth bound.**

⚠️ Those figures were not measured with this methodology
([Notes and Caveats 1)](../FINDINGS.md#notes-and-caveats)).

There is a public report in the other direction too — on an RTX 3090 with
Qwen3.6-35B-A3B every speculative mode was slower than baseline
[{ref 10.}](../FINDINGS.md#references). That model is an MoE, so the cause may differ,
and no batch cost decomposition was done.

## 4. MTP is a variance problem more than an average problem

Warm 4-turn `tg` spread:

| Cell | Warm 4 turns | Spread |
|---|---|---|
| tensor / MTP off / 4 | 17.94 / 17.91 / 17.86 / 17.84 | **0.6%** |
| layer / MTP off / 2 | 8.12 / 8.09 / 8.06 / 8.06 | 0.8% |
| layer / MTP on / 4 | 6.51 / 6.19 / 6.63 / 6.86 | 10.1% |
| tensor / MTP on / 4 | 13.17 / 13.92 / **17.90** / 14.28 | **31.9%** |
| tensor / MTP on / 3 | 11.34 / **19.60** / 10.65 / 11.81 | **67.0%** |

The second warm turn of `tensor / MTP on / 3` hit **75% acceptance** (276 of 368) and
produced 19.60 t/s. MTP shines when it meets an easily predicted passage, but
**there is no telling when such a passage will arrive.**

The average is a loss and the response time is erratic, so the perceived quality is
worse than the average suggests.

**On V100 the MTP-on spread was still 12~17%.** The variance survives even after the
average turns into a gain — it is intrinsic to speculative decoding, not a defect of
this card.

## 5. Appendix A — private fixture (not reproducible)

The work in this document **began with an experiment on a private fixture** (the
private fixture is sensitive data and cannot be published).

**The published results in this document contain no results from the private
fixture**; they consist solely of data from the fixture provided here.

The two fixtures are reported together because **they agreed to within 1% under the
MTP-off conditions.** Getting the same result from texts of very different character
is evidence that the published results do not depend on the text. Under MTP-on
conditions, by contrast, **they did differ, and that contrast is itself information.**

Only the following data from the private fixture is published, **so judge its
reliability for yourself.** It was produced with the same harness, the same token
counts and the same cell definitions as the public fixture.

## 6. Limits specific to this platform

1. **The single-GPU baseline is derived.** The model (13,115 MiB) does not fit on one
   8GB card. The scaling efficiency in the
   [derived metrics document](p104-100-x4-metrics.md) depends on that derivation.
   **V100 16GB measured a single card and confirmed the derivation to within 1%**
   ([Notes and Caveats 2)](../FINDINGS.md#notes-and-caveats)) — but the value for this
   platform is still derived
2. **`layer / MTP on / 2 cards` is empty.** Compute buffer OOM
3. **Tensor parallelism changes the output as N changes.** `draft_n` differs across
   the 4, 3 and 2 card cells of `tensor / MTP on` (675 / 642 / 660 …) because a
   different operation order produces different tokens. By contrast, `layer / MTP on`
   at 4 and 3 cards gives **identical** `draft_n` and `draft_n_accepted` every turn
   (V100 confirmed this down to 1 and 2 cards).
   → **MTP comparisons between tensor-parallel cells are not controlled for generated
   content**
4. **Measured under v1.1, so there is no clock or throttle record.** No judgement about
   temperature is possible
